# 关卡编辑器 Go 后端说明

## 目标

当前编辑器已经可以载入、编辑和导出地图，但手动复制配置回源码不适合长期使用。Go 后端的第一版目标是提供本地开发用地图存储接口，让编辑器后续可以直接读取和保存地图。

## 第一版范围

- 使用 Gin 组织路由和中间件，方便后续继续加地图、资源、用户等 CRUD。
- 不接数据库，地图保存为本地 JSON 文件。
- 不做登录、权限、多人协作。
- 每次保存自动追加一个历史版本。
- 前端 Vite 开发环境可以通过 CORS 访问接口。

## 数据模型

服务端保存的核心对象是 `GameMapConfig`，字段和前端运行时地图配置保持一致：

- `id`
- `name`
- `spawnPoint`
- `requiredKills`
- `groundMaterial`
- `colliders`
- `props`
- `doors`

外层额外保存：

- `mapKey`
- `status`
- `levelNo`
- `levelTheme`
- `createdAt`
- `updatedAt`

`groundMaterial` 不需要单独新增数据库列，它和地图对象、碰撞体、门一样保存在 `maps.config` 与 `map_versions.config` 的 JSON 快照里。后端 Go 结构体需要声明该字段，否则保存时重新序列化会把它丢掉。

`levelNo` 和 `levelTheme` 是地图元数据，需要单独存在 `maps` 表上。它们用于后端地图列表、编辑器关卡切换和游戏默认地图顺序，不跟随 `GameMapConfig` 一起放进 JSON：

- `levelNo = 1, levelTheme = graveyard`：第一关 / 墓地。
- `levelNo = 2, levelTheme = mini_market`：第二关 / 便利店。

旧地图没有这两个字段时，后端会按 `map_key` 和 `props[].assetId` 做兜底推断；新保存的地图以编辑器提交的字段为准。

## 接口

- `GET /api/maps`：地图列表。
- `POST /api/maps`：新建地图。
- `GET /api/maps/{mapKey}`：读取地图。
- `PUT /api/maps/{mapKey}`：更新地图。
- `DELETE /api/maps/{mapKey}`：删除地图。
- `GET /api/maps/{mapKey}/versions`：读取历史版本。

## 后续接入编辑器

编辑器和游戏运行时已经接入后端地图接口：

- “从后端载入地图”
- “保存”
- 游戏地图弹窗从后端读取地图列表
- 游戏启动时从后端读取地图配置

暂未接入：

- “另存为”
- “查看历史版本”

编辑器仍然保留导出 TypeScript 配置能力，用于调试和人工备份。正式运行时地图数据以数据库为准。

## 地图数据来源

前端运行时不再保留本地地图注册表，而是统一通过 `/api/maps` 从后端读取。

编辑模式不会从本地地图文件载入地图，也不会在数据库为空时自动写入本地 seed。数据库为空时，编辑器只提示后端暂无地图。

## 前后端地址

前端统一通过 `/api` 访问后端接口。

开发环境：

- Vite 会把 `/api` 代理到 `http://127.0.0.1:8088`。
- 前端代码不直接写死本机端口。

部署环境：

- 推荐把前端静态资源和 Go 后端放在同一个域名下。
- 由 Nginx 或服务器网关把 `/api` 反向代理到 Go 服务。
- 这样浏览器访问的仍然是同域 `/api`，不需要额外处理跨域。

如果后续前端和后端必须分成不同域名，可以在构建前设置：

```bash
VITE_API_BASE_URL=https://api.example.com/api
```

此时前端会直接访问该完整后端地址。
